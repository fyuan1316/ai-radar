# K8s AI 基础设施周报 2026-09-24

窗口:2026-09-17 -> 2026-09-24(7 天)。与 2026-09-22 期重叠的条目(Kueue v0.19.5/v0.18.9、LWS #1050、KEP-6089、k8s #141932 workload preemption)已在上期报过,本期不重复,只在有新进展处引用。

## 摘要(3 条以内)
- **DRA 迎来一轮"毕业潮"**:KEP-4815 Partitionable Devices 冲 GA、KEP-5517 Node Allocatable 与 KEP-6080 Derived Attributes 冲 1.38 beta,叠加 KEP-5690 DRA 抢占、KEP-6406 扩展资源映射容量请求。DRA 取代 device-plugin 的路线从"可用"进入"成熟/GA"阶段,直接影响所有加速器方案选型。
- **上游原生 gang/PodGroup 本周实锤推进**:kube-scheduler 主仓合入 PodGroup snapshot 增删接口([#142177](https://github.com/kubernetes/kubernetes/pull/142177)),KEP-6012 CompositePodGroup API 定 1.38 beta,KEP-6413 新增 PodGroup 运行时满足度条件、KEP-5710 细化 PodGroupPreemptionPolicy 毕业标准。**Volcano 的 gang 独占性被进一步稀释**。
- **LWS v0.11.0 发布并原生落地 KEP-666 workload-aware gang scheduling**([#979](https://github.com/kubernetes-sigs/lws/pull/979)/[#982](https://github.com/kubernetes-sigs/lws/pull/982)/[#1072](https://github.com/kubernetes-sigs/lws/pull/1072)),多节点推理/训练拓扑开始直接对接上游 WAS 而非仅依赖 Volcano PodGroup;同期依赖已 bump 到 k8s v1.37。

## GPU / 加速器管理

- [NVIDIA gpu-operator v26.7.1](https://github.com/NVIDIA/gpu-operator/releases/tag/v26.7.1)(09-23)— patch 版本,详情见 [官方 release notes](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/26.7/release-notes.html#v26-7-1)。
  - 启示:26.7 线进入维护期,生产集群跟 patch 即可;无架构级变化。
- [NVIDIA k8s-device-plugin v0.20.1](https://github.com/NVIDIA/k8s-device-plugin/releases/tag/v0.20.1)(09-22)— 加固为主:NodeFeature CR 删除权限、DaemonSet selector 去重叠、vGPU 能力记录长度校验、greedyAlloc 用最小堆替换每次排序、GFD PCI 厂商能力解析防坏长度。
  - 启示:多条"校验坏长度/权限收敛"修复说明 device-plugin 在往稳态收尾,新能力重心已明显转向 DRA。vGPU 记录长度校验对我们做 vGPU 纳管的健壮性有参考价值。
- [Kubernetes PR #141118](https://github.com/kubernetes/kubernetes/pull/141118)(09-18)— DRA 拒绝 `ResourceSliceCount` 不一致的 pool。
  - 启示:DRA pool 的一致性校验在收紧。我们做设备发布/切片层时,ResourceSlice 分片计数必须与实际 slice 数严格对齐,否则会在 admission 被拒。

## 调度 & 资源分配

### 上游原生调度(WAS / gang / Workload API)
> 常设研判题:本周 WAS/gang 进展,挤压还是利好 Volcano / Kueue / KAI?

- [Kubernetes PR #142177](https://github.com/kubernetes/kubernetes/pull/142177)(09-23)— 在调度器 snapshot 中新增 `AddGenericPodGroups` / `RemoveGenericPodGroup`;配套 [#142219](https://github.com/kubernetes/kubernetes/pull/142219) 收敛 `QueuedPodGroupInfo` 内部字段。
  - 研判:GenericWorkload/PodGroup 的**调度快照数据结构已在主仓落地**,这是 v1.36→1.37 原子成组调度周期的地基。**挤压 Volcano**:上游正在把"成组感知"做进 scheduler 内核而非留给外置批调度器。
- [KEP-6012 CompositePodGroup API](https://github.com/kubernetes/enhancements/pull/6348) — 定 v1.38 beta。
  - 研判:PodGroup 的上游标准 API 形态逐渐清晰(Composite = 一个 workload 内多种 PodSet 组合)。这正是 Volcano PodGroup / scheduler-plugins Coscheduling 长期占据的地盘,一旦 beta,生态调度器的差异化只剩"策略丰富度"而非"有没有 gang"。
- [KEP-6413 PodGroup runtime satisfaction condition](https://github.com/kubernetes/enhancements/pull/6414) — 新增 PodGroup 运行时满足度(min-member 是否已就绪)的标准 condition。
  - 启示:未来判断"gang 是否成组"可读上游标准 status,我们的控制面/UI 不必再各自解析 Volcano/Coscheduling 私有状态。
- [KEP-5710 workload-aware preemption](https://github.com/kubernetes/enhancements/pull/6420) — 细化 `PodGroupPreemptionPolicy` 毕业标准与优先级校验(上期 k8s #141932 的 KEP 侧)。
  - 研判:原生抢占正在补 gang 语义(整组抢占/整组豁免),利好把训练任务最小运行时、checkpoint 纳入抢占决策;进一步压缩生态调度器在"抢占策略"上的独占价值。
- [KEP-6276 Integrate Workload APIs with Deployment controller](https://github.com/kubernetes/enhancements/pull/6295) — 让 Deployment 也能挂 Workload API。
  - 启示:WAS 不再只服务批作业,开始下沉到最常见的 Deployment,长期是"所有 workload 默认可被调度器感知成组"的方向。
- [LWS v0.11.0](https://github.com/kubernetes-sigs/lws/releases/tag/v0.11.0)(09-23)原生 gang 系列:[#979 KEP-666 Gang Scheduling](https://github.com/kubernetes-sigs/lws/pull/979)、[#982 Phase 1 workload-aware gang](https://github.com/kubernetes-sigs/lws/pull/982)、[#1072 groupIdentity Hash 支持 WAS](https://github.com/kubernetes-sigs/lws/pull/1072)。
  - 研判:**利好上游、挤压 Volcano**。LWS 作为 OAI 已用的多节点推理方案,选择对接上游 WAS gang 而非把 gang 完全外包给 Volcano。注意同版本仍有 [#1076](https://github.com/kubernetes-sigs/lws/pull/1076)/[#1057](https://github.com/kubernetes-sigs/lws/pull/1057) 修 Volcano PodGroup 兼容——过渡期两条路径并存,但战略方向已偏向原生。

### Kueue
- [Kueue PR #15577](https://github.com/kubernetes-sigs/kueue/pull/15577)(09-23)— DRA:admission 前**逐节点**检查设备可用性。
  - 启示:Kueue 的 DRA 路径从"配额记账"进到"节点级可行性预检",避免 admit 了却无节点可放。我们做 DRA 队列时必须把 per-node 设备可用性纳入 admission,否则会出现"入队成功、永久 pending"。
- [Kueue PR #15983](https://github.com/kubernetes-sigs/kueue/pull/15983)(09-24)— DRA:抽出扩展资源采集与扣费 helper;[#16062](https://github.com/kubernetes-sigs/kueue/pull/16062)(09-23)新增可配置抢占的 Evaluator。
  - 研判:Kueue 持续把 **DRA + Workload 当默认路径**在打磨(记账/扣费/抢占评估器化)。与上游 WAS 是"互补而非对抗":Kueue 站在 queue/quota 层,把成组调度交给下游 scheduler。这是生态调度器被上游挤压后最可能的存活位——退到配额与多租户治理层。
- [Kueue PR #14578](https://github.com/kubernetes-sigs/kueue/pull/14578) — 修复空 StatefulSet / LeaderWorkerSet PodGroup 的驱逐;[#16039](https://github.com/kubernetes-sigs/kueue/pull/16039) 校验 StatefulSet 更新时的 TAS 元数据。
  - 启示:Kueue 对 LWS/StatefulSet 的 PodGroup 集成在补边界。做 LWS+Kueue 组合时,空组驱逐与 TAS 拓扑元数据校验是易踩坑点。

### Volcano / Kthena
- [Volcano PR #5848](https://github.com/volcano-sh/volcano/pull/5848)(09-22)— scheduler 用 queueing hints 缓存不可调度作业;[#5928](https://github.com/volcano-sh/volcano/pull/5928)(09-22)nodeorder 打分插件单次节点遍历完成(性能)。
  - 启示:Volcano 在补调度吞吐/延迟。面对上游原生 gang 的挤压,Volcano 的差异化正转向"大规模队列下的调度性能与策略丰富度",这与上游 WAS 的定位差正是我们选型的关键判断点。
- Kthena(volcano-sh)本周推理路由密集迭代:[#1725](https://github.com/volcano-sh/kthena/pull/1725)/[#1758](https://github.com/volcano-sh/kthena/pull/1758) KV cache 感知路由(内存索引 + 本地 tokenizer 服务)、[#1144](https://github.com/volcano-sh/kthena/pull/1144) Model Router 会话粘连、[#1705](https://github.com/volcano-sh/kthena/pull/1705) router 可脱离 K8s API server 独立运行。
  - 启示:Kthena 与 KServe/InferNex 推理路由同赛道,KV-cache-aware 路由 + 会话粘连是 PD 分离推理的关键能力,openFuyao 大概率跟进,值得对标我们的推理网关。

### DRA
> DRA 是重中之重(取代 device-plugin,影响所有加速器方案)。本周为集中毕业窗口:
- [KEP-4815 DRA Partitionable Devices → GA](https://github.com/kubernetes/enhancements/pull/6381) — GPU/加速器"可分片设备"进 GA。
  - 启示:**MIG/切片类共享的上游标准即将 GA**,这是 HAMi/vGPU 类方案长期要对齐的靶子。我们的加速卡分片能力应规划向 DRA Partitionable Devices 迁移。
- [KEP-5517 DRA Node Allocatable Resources → beta](https://github.com/kubernetes/enhancements/pull/6324)、[KEP-6080 DRA Derived Attributes → beta(1.38)](https://github.com/kubernetes/enhancements/pull/6255)。
  - 启示:节点可分配 DRA 资源与派生属性进 beta,DRA 的资源模型日趋完整,可用于生产评估。
- [KEP-5690 DRA preemption](https://github.com/kubernetes/enhancements/pull/6113)(新提案)、[KEP-6406 DRA 扩展资源映射支持容量请求](https://github.com/kubernetes/enhancements/pull/6408)。
  - 启示:DRA 补上抢占与"把 DRA 设备映射成扩展资源 + 容量请求"能力后,才能真正无缝替换 device-plugin 的 `nvidia.com/gpu` 语义,兼容存量调度逻辑。这条对我们平滑迁移最关键。

### LWS / JobSet
- [LWS v0.11.0](https://github.com/kubernetes-sigs/lws/releases/tag/v0.11.0) 除上文 gang 外:DisaggregatedSet 补 status/条件与 Service 归属([#980](https://github.com/kubernetes-sigs/lws/pull/980)/[#1004](https://github.com/kubernetes-sigs/lws/pull/1004)/[#1079](https://github.com/kubernetes-sigs/lws/pull/1079))、[KEP-960 虚拟子角色](https://github.com/kubernetes-sigs/lws/pull/961)、依赖 bump 到 k8s v1.37([#1012](https://github.com/kubernetes-sigs/lws/pull/1012))。
  - 启示:LWS 的 DisaggregatedSet(PD 分离)在补齐可观测性与生命周期语义,是多节点 disaggregated 推理的原生底座,与 Kthena 的路由层可组合。
- JobSet 本周仅依赖/示例修复,无高价值功能更新。

## KEP 动向
- **DRA 毕业潮**(详见"DRA"节):KEP-4815 GA、KEP-5517 / KEP-6080 beta、KEP-5690 抢占、KEP-6406 扩展资源映射——本期最值钱的信号,决定我们加速器路线 6 个月后的选型。
- **PodGroup/Workload API 主线**:KEP-6012 CompositePodGroup(1.38 beta)、KEP-6413 运行时满足度条件、KEP-5710 抢占策略毕业标准、KEP-6276 Deployment 集成——上游原生成组调度成型中。
- [KEP-6274 GPU 支持 Pod 级 Checkpoint/Restore](https://github.com/kubernetes/enhancements/pull/6275) — GPU 作业的 checkpoint/restore 上游化,长期利好训练容错与抢占后恢复。

## 值得跟进
- [ ] **DRA 迁移规划**:评估自家加速卡分片/vGPU 能力向 KEP-4815 Partitionable Devices(GA)对齐的路径,以及 KEP-6406 扩展资源映射对存量 `nvidia.com/gpu` 语义的兼容迁移。
- [ ] **WAS 常设研判**:跟 KEP-6012 CompositePodGroup beta 与 k8s #142177 PodGroup snapshot,判断 12 个月后我们是否还需自定义 PodGroup/Queue API,还是直接消费上游 GenericWorkload。
- [ ] **Kueue DRA 路径**:把 per-node 设备可用性预检(#15577)纳入我们多租户 GPU/NPU 队列的 admission 设计,避免"入队即 pending"。
- [ ] **LWS v0.11.0 落地评估**:KEP-666 原生 gang + DisaggregatedSet status 是否可替代我们现有多节点推理编排;注意其已依赖 k8s v1.37。
- [ ] **Kthena 对标**:KV-cache-aware 路由 + 会话粘连 vs 我们推理网关的能力差。
