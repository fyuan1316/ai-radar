## 调度(kube-scheduler)

- **KEP-6438 Resize Gates for In-Place Pod Resize**(新建 provisional,PR #6459,sig-node + sig-scheduling):为 in-place pod resize 引入"resize gate"机制,让**树外的配额控制器**在一次 in-place 扩容被真正应用前先行准入——不准入就把扩容挂起。承接 kubernetes/kubernetes#131835 的设计讨论,9 月已在 SIG Scheduling 过会,SIG Node 跟进中。对我们产品意义见"自动扩缩容"与"值得跟进"。https://github.com/kubernetes/enhancements/pull/6459
- **DRA 侧**(KEP-5981 DRA Sharing Affinity for Consumable Capacity,PR #5987 已合):属 DRA 设备层,按边界约定归 `k8s-ai-infra`,此处不展开;仅提示它改的是 ResourceClaim 共享语义,对所有 DRA 用户有溢出,关注 `k8s-ai-infra` 本周篇。
- 其余本周无通用调度器(preemption / topology / affinity)的实质能力变更。

## 节点 & kubelet

- **KEP-5714 cgroup namespace unshare**(PR #5715 已合、approved;followup PR #6462):允许在 Pod 级别指定**是否 unshare cgroup namespace**(cgroup v2 下默认每容器独立 cgroup ns,此特性让你能退回共享语义)。#6462 修正 POD namespace 模式应映射到 CONTAINER。对需要容器内看到宿主 cgroup 层级的监控/运行时场景有用。https://github.com/kubernetes/enhancements/pull/5715
- **KEP-6416 Kubelet Parallel Container Operations**(PR #6419,WIP,目标 Alpha v1.38):让 kubelet 对同一 Pod 内的部分容器操作**并行执行**,目标降低多容器 Pod 的启动/关闭串行延迟。对 sidecar 密集、init 链长的工作负载(典型:AI 推理 + 代理 sidecar)有直接启动提速价值。https://github.com/kubernetes/enhancements/issues/6416
- **KEP-6467 init 容器启动状态可见性**(新建 provisional,PR #6468,sig-node + sig-cli):正在被准备启动的 init 容器报 `ContainerCreating`、仍在等前序 init 的报 `PodInitializing`,区分"卡在拉镜像"与"排队等前序",排障体验改善。https://github.com/kubernetes/enhancements/pull/6468
- **KEP-6313 Non Network / network-isolated Pods**(PR #6317 已合,stage/alpha,sig-network + sig-node):允许 Pod **退出自动集群网络编排**,拿到一个严格隔离的专用 network namespace。对需要强网络隔离的敏感批处理/安全沙箱有用。https://github.com/kubernetes/enhancements/issues/6313
- **KEP-6262 Job Pod 节点维护期替换**(PR #6402,sig-apps + sig-node + wg/node-lifecycle):节点维护(`MaintenanceInProgress` 条件)导致 Pod 到不了终态时,`podReplacementPolicy: Failed` 的 Job 可据此判定可替换,避免 Job 与上层队列系统(Kueue 等)无限卡住。https://github.com/kubernetes/enhancements/issues/6262
- 维护性:KEP-4639 标记 implemented(PR #5960 已合)、KEP-5328 Node Declared Features 推进(PR #6466)。

## 自动扩缩容(VPA / CA / Karpenter)

- **Karpenter v1.15.0**(2026-10-10,正式 release),本窗口最有料的扩缩容发布:
  - **VPA prediction controller and store(#3134)**:Karpenter 开始内建 VPA 预测控制器与存储——节点扩缩容与垂直伸缩在同一控制器里耦合预测,值得盯这条"调度器感知 Pod 将要变大"的线。
  - **默认 Pod topology spread 感知(#3205)**、**按实例类型卷上限 provisioning(#3202)**:provisioning 决策更贴近真实约束。
  - **node repair as voluntary disruption(#3311)**、**reboot 作为 node action(#3345)**、容量受限 NodePool 的 **terminate-first drift/repair(#3312 / #3342)**:节点自愈/重启被纳入统一的中断(disruption)模型。
  - **DRA prioritized alternatives(#3142)**:DRA 相关,归 `k8s-ai-infra`,此处不展开。
  - 大量 disruption 指标细化(`karpenter_pods_disrupted_total` 等)。https://github.com/kubernetes-sigs/karpenter/releases/tag/v1.15.0
- **VPA**:仅 helm chart `vertical-pod-autoscaler-chart-0.14.0`(2026-10-13)发布,无 VPA 本体能力变更。VPA 的真正解锁仍押在 in-place resize 线上(见下方 KEP-6438)。https://github.com/kubernetes/autoscaler/releases/tag/vertical-pod-autoscaler-chart-0.14.0
- **in-place resize 这条线合看**:KEP-1287(GA)解决"原地改大/改小不重建 Pod",KEP-6438(本周新建)解决"改大之前先过配额闸门"。两者齐了,VPA 在多租户生产环境才真正敢开。
- **Cluster Autoscaler**:本周无实质能力发布。

## 值得跟进

- [ ] **读 KEP-6438 Resize Gates**(https://github.com/kubernetes/enhancements/pull/6459)+ 设计源 kubernetes/kubernetes#131835:评估我们多租户配额体系要不要实现一个 resize gate 控制器,否则 in-place 扩容会绕过配额准入——这是 VPA 在我们产品生产化的前置条件。
- [ ] **立即规划 containerd 升级**到 v2.4.2 / 2.3.7 / 2.2.10 / 2.0.14(https://github.com/containerd/containerd/releases/tag/v2.4.2):盘点节点池在用 containerd 分支,安排安全补丁 rollout;重点关注镜像拉取内存暴涨修复对大镜像(AI 模型层)节点的稳定性影响。
- [ ] **跟 Karpenter VPA prediction controller(#3134)**:看 Karpenter 把"Pod 将要变大"纳入扩容决策的做法,对我们自研调度/扩缩容的"预测性 provisioning"有借鉴(https://github.com/kubernetes-sigs/karpenter/releases/tag/v1.15.0)。
- [ ] **评估 Gateway API v1.7 的 Pre-routing Filters(GEP-5224)与 TelemetryPolicy(GEP-4768)**:若产品网关面要接外部鉴权/标准化追踪,这两个 GEP 决定要不要等 v1.7 正式版再做(https://github.com/kubernetes-sigs/gateway-api/releases/tag/v1.7.0-rc.1)。
- [ ] **关注 KEP-6416 Parallel Container Ops**:若落地 1.38 alpha,测它对 sidecar 密集推理 Pod 的启动提速(https://github.com/kubernetes/enhancements/issues/6416)。
