## 本周精选(5 篇)

- **[Validation-driven Deployment of LLM Inference Platforms for Agentic Workloads](https://arxiv.org/abs/2611.25905)**(11-19,IBM Research + Red Hat AI)— 本期第一篇该看的:一套把 agentic 推理平台从"测试→抓流量→定容→预生产→生产"打通的验证方法论,案例就是在 **llm-d** 上滚四个 MoE 大模型。
  - 核心思路:作者指出企业自建推理平台的真问题不在引擎快慢,而在**定容和验证的输入是错的**。公开 trace(WEKA、NVIDIA Moontrace)丢掉了请求正文,没法对着目标模型重放;而 agent 会话的形状(逐轮增长的上下文、并行工具调用、子 agent 扇出、工具执行期的空窗)决定了容量,所以"用不像自己流量的 trace 定容,得出的容量在生产上不成立"。方案是五阶段流水线:小规模功能门禁(chat/streaming/tool calling/reasoning/结构化输出/畸形请求)→ 用真 agent 跑 benchmark 抓**带正文的全量 trace** → 升压重放找吞吐饱和点 → 预生产做版本比对与优先级/公平性争用验证 → 生产按租户在 router 与 engine 两侧分别跟踪。
  - 关键数据点:**重放 vs 现场重跑的保真度差一个量级**——按会话 token 总量算,重放的 P95 输入比 1.12–1.18x、现场重跑 3.97–4.98x(即重跑会严重漂移);工具调用保真度 0.87–0.90 vs 0.20–0.30。用**捕获 trace 定容,得到的最优并发只有公开 trace 结论的约一半、单卡吞吐约 60%**(四个目标模型一致)。vLLM v0.31.0 代码覆盖实测:live/重放/合成三类负载各自能摸到别人摸不到的路径(并集 9,778 条语句、437 条独占),且**没有任何一类负载走到 CPU→GPU 的 KV 恢复路径**,要靠专门构造的合成负载(200 组 65,536-token 共享前缀、约 1.37x GPU KV 池)才多覆盖 124 条。代表性上,五个 benchmark 对 GLM-5.3 真实 4 天约 220 万请求的 KS 距离全都不小(HWE-Bench 0.135/0.044 最好、WEKA 0.223/0.212 最差)。
  - 对我们的启示:这篇等于把"推理平台怎么验收"这件我们一直靠经验做的事写成了可抄的 SOP,而且是在 llm-d 上做的——对标 OAI 时这就是对面的作业本。产品决策级动作:(1) **把"抓真实 agent trace + 带正文重放"做成平台自带能力**,而不是售前拍脑袋按公开 benchmark 报容量;作者把 OTel trace 重放和合成 agentic 生成贡献进了 `kubernetes-sigs/inference-perf`(https://github.com/kubernetes-sigs/inference-perf),我们可以直接接而不是自研。(2) **容量承诺口径要改**:公开 trace 只能用于初始调参,定容必须用目标模型自己产的 trace,否则会超卖约 2x(并发)/高估约 40%(吞吐)。(3) 他们在 Terminal-Bench 2.1 上踩到的 **router bug 值得我们直接当回归用例**:会话共享约 17K token 的工具定义 + 26–27K 字符 system prompt 时,prefix-affinity 打分把流量全压到少数几个 replica,根因是 token producer 用的是**估算 tokenization 而非精确 tokenization**——WEKA 这类无共享前缀的 trace 永远测不出这个 bug。我们自家 router 若也有 KV 亲和打分,必须补一条"大共享前缀"的压测。(4) 覆盖率那条提醒我们:KV offload 的恢复路径在常规压测里是**死区**,上线前要专门造负载打它。

- **[BlockJack: Cross-Tenant Redirection Fault Attacks on Paged KV Cache Address Translation in LLM Serving](https://arxiv.org/abs/2611.25945)**(11-19)— 只翻一个 block table 表项,就能让攻击者的 KV 读指向受害租户的缓存块;vLLM 已确认并与 Sonar 各自出了补丁。
  - 核心思路:攻击面不是权重、不是 prompt、也不是缓存的 KV 内容,而是 **paged KV cache 的"地址翻译"元数据**——把逻辑块号映射到物理块 ID 的 block table。改一个表项就有两种后果:Context Disclosure(改攻击者自己的表项指向受害者的块,受害者上下文出现在攻击者的回答里)和 Response Alteration(改受害者的表项指向攻击者的块,用攻击者投喂的上下文操纵受害者的答案)。同索引重定向连 RoPE 对齐都不破,跨索引只引入一个常数位置偏移、内容照样泄露。作者还给出了"重定向目标何时可预测"的刻画:新实例的空闲队列按 ID 升序发放,目标可由公开配置推出;攻击者可以通过加长请求或塞哑请求来塑形自己拿到的块 ID。
  - 关键数据点:**物理可行性用 Rowhammer 实测**——vLLM 0.25.0 的 CPU 后端把 block table 放在 host memory 的一个 8 KiB int32 tensor 里,DDR4 平台上 20 轮 90 分钟的 campaign 里 142 个 hammering 窗口有 70 个(49%)产生了预期重定向,CD 在 10 轮中 3 轮、RA 在 10 轮中 8 轮验证成功。完整性危害量化在一个 248 场景的医疗分诊 benchmark(源自 ChatDoctor-HealthCareMagic-100k):跨 7 个模型(Qwen2.5-1.5B/7B、Llama-3.2-1B/3.1-8B、Gemma-2-2b/9b、Phi-3.5-mini)× 5 个 LLM judge,**"隐蔽降级率"(回答把病情说得更不紧急、同时读起来仍与问题自洽)在 5.2%–41.1% 之间**。披露时间线:2026-09-15 报 vLLM 与 SGLang、09-22 vLLM 确认,09-24 报 Sonar、11-10 Sonar 维护者独立复现;防御是 host 侧独立记一份 scheduler 分配的块 ID、用前校验表项,两家各自实现并挡住了测试中的篡改(论文未给开销数字,也未给 CVE 与受影响版本区间)。
  - 对我们的启示:过去两年推理侧**所有性能收益的来源——prefix cache / KV 复用 / 分页管理——第一次被证明是一条跨租户的数据通路**,而且元数据比数据更脆弱(一个表项 vs 整块 KV)。产品决策级动作:(1) **把"prefix cache 跨租户复用"做成显式、可按租户/按命名空间关闭的开关,并默认在多租户共享实例上关闭**;现在多数部署是"默认开、全局共享",这篇之后这个默认值在金融/医疗客户那里是过不了合规评审的。(2) **block table 的完整性校验要进我们的推理镜像基线**,跟进 vLLM 侧补丁并把版本下限写进产品的受支持矩阵;同时注意作者只在 CPU 后端做了端到端 Rowhammer,GPU 内存里的 block table(vLLM v0.25 起 dense 模型默认的 MRV2)需要 GPU Rowhammer、论文留作 future work——**这不等于 GPU 后端安全,只是尚未被打穿**。(3) 威胁模型要求**物理同机共驻**(攻击者只需非特权软件访问 + 请求进同一个 serving 实例的同一块池),所以我们的租户隔离策略应当明确:高敏感租户不与他人共享 serving 实例与块池,Pod/节点级隔离在论文里**未被证明足够**。(4) 同周还有两篇把 KV 共享的另两面捅破:[When Shuffling Fails](https://arxiv.org/abs/2611.24276)(11-18)把 KV-Cloak 这类"线性变换+置换"混淆的有效状态空间从 b! 塌缩到 b,3,000 条真实 WildChat prompt 上**100% 还原 token 多重集**;[From Token Changes to Task Failures](https://arxiv.org/abs/2611.22243)(11-17)量化了共享 system prompt 那**一份物理 KV 块**上一次比特翻转的实际危害(TriviaQA 上 0.59–0.60 的变化会把正确答案改错,MBPP+ 约 0.02),并建议靠校验缓存块而非监控输出来检测。三篇合起来是"KV 共享的安全/可靠性"这个新议题的开场。

- **[Berth: SLO-Preserving GPU Sharing Without New Preemption](https://arxiv.org/abs/2611.25091)**(11-18)— 推理服务按峰值预留的 GPU 空着,想塞训练又会打崩 SLO;Berth 不改应用、框架、内核、驱动,只在用户态控制"什么时候让 best-effort 有活在排队",就把优先级造出来了。
  - 核心思路:作者的观察很锋利——**NVIDIA 自带的时间片切换本身够快(亚毫秒级抢占 + 空闲即切),缺的只是优先级**;那么优先级可以从外部造:用 LD_PRELOAD 式 shim 钩住 CUDA driver 的 kernel launch 路径(扩展 libsmctrl,让闭源库 cuBLAS/cuDNN 的 launch 也能被看见),best-effort 的 launch 直接把发起线程阻塞在驱动里(队列 0.2ms 内能排空就 spin、否则按 20µs 步长 sleep),并保证 GPU 上最多只排着 f = 1ms 的预测 best-effort 工作量(kernel 时长来自 CUPTI 约 12s 标定出的 profile,CUDA graph 按一次 launch 计)。对**连续批处理的 LLM 引擎**,它不靠"请求到达"而是给每个 step 算一个截止参考 `need_by = b + D − r − g`(b 步开始、D 每 token/step 预算、g 为 20%D 且不小于 2ms 的护栏、r 为 EWMA 观测步时乘未发射工作占比),只在 `t + f + c < need_by`(c = 0.3ms 切换开销)时放行 best-effort。另外拦下驱动的 `NVA06C_CTRL_CMD_SET_TIMESLICE` ioctl,把 best-effort 上下文的时间片从 2,048µs 改写成 **500µs**(延迟敏感侧保持默认),一个 watcher 每 1ms 采样、没有在飞请求时恢复原值。
  - 关键数据点:动机实测就很说明问题(ResNet-50 batch 8 / 15ms SLO,旁边跑 BERT-large 训练):**MPS 空间共享下 SLO 达标率 0.0%、默认时间片 64.9%**,而单独跑是 97.3%;TGS 能到 96.8% 但训练只跑出 6% 的速度。Berth 在 **31 个 MLPerf SLO 场景点 × 13 个基线**(time-slicing、MPS 及其 priority/limits/静态分区、TPC 配额即 LithOS 式重实现、DySM 式、XSched、multi-stream、TGS、MIG、Tally、Orion)上:平均 SLO 达标 **95.8%**(单独跑 97.9%),高于所有基线(MIG 88.4%、MPS 静态分区 87.1%、TPC 配额 85.5%、Orion 52.8%、裸时间片 48.9%),同时 best-effort 吞吐是**最接近的几个基线的 2.7–3.5x**(绝对值:单独跑的 48%,四个最近基线 14–18%)。vLLM 0.11.0 + Qwen2.5-1.5B/0.5B 的 7 个点上,**最差租户仍能满足 99.8–100% 的 per-token 目标**,而训练照跑。消融:只有喂给式节流 82.9% → 加分层喂给+短时间片 91.9% → 加 0.5ms 宽限期 94.2%(按最差租户算)。探针实验里时间片从 2,048µs 改到 500µs 让小 kernel 的 p99 从 2.25ms 降到 0.55ms(100µs 反而更差)。
  - 对我们的启示:这篇直接打在我们 HAMi/vGPU 线的痛点上——**"推理按峰值预留"是客户买卡最大的浪费项,而我们目前能给的只有显存切分和裸时间片两档**,而裸时间片在 15ms 级 SLO 下达标率不到 65%。产品决策级动作:(1) **把"延迟敏感 + best-effort 混跑"做成一等场景**,机制上采 Berth 这条"用户态喂给式节流 + 改写时间片"的路线,而不是去改调度器/驱动——因为它的最大卖点正是**不改应用/框架/内核/驱动**,这对我们在客户已固化的 GPU 栈上做增量交付是决定性的;对应代价是需要 per-model/per-GPU 的 kernel profile(约 12s 标定)和依赖驱动内部 RM control 接口,这两条要写进工程评估。(2) **对 LLM 引擎,混跑的准入判据必须是"step 截止参考",不是"GPU 利用率"**——Berth 的 `need_by` 公式可以直接作为我们调度器里"是否放行低优工作"的实现蓝本。(3) 作者自述的盲区正是我们要补的差异化:**看不到请求队列,所以突发和接近饱和时最弱**;我们的控制面能看到网关/队列深度,把队列信号喂进这个节流器就能做得比论文更稳。(4) 同周的 [BubbleTea](https://arxiv.org/abs/2611.24496)(11-18)是同一主题的更细粒度版本——MoE 专家并行在 **层内**留下的 0.29ms 级气泡(SOTA 负载均衡后仍占 prefill 时间 8–13%)也能回收,用来跑 LoRA 微调 chunk;两篇一起说明"回收闲置算力"的粒度已经从"卡/时间片"下探到"层内毫秒"。
  - 代码:论文未给仓库地址(作者用了 XSched/TGS/Orion/Tally 的已发布代码做基线)。

- **[TripleKV: Predict, Prefetch, Protect — KV Cache Management for AI Agents](https://arxiv.org/abs/2611.25112)**(11-18)— agent 在等工具返回的几十秒里,它那几 GB KV 要么占着显存、要么被踢到 SSD 回来要 1–2.5 秒;TripleKV 用"预测工具何时结束"来决定什么时候把 KV 搬回 DRAM。
  - 核心思路:三层(L1 GPU HBM / L2 host DRAM / L3 SSD)上做三件事。**Predict**:在 agent harness 里按工具维护延迟历史,结合调用参数与实时输出、分工具类型用不同方法预测这次工具调用何时结束。**Prefetch**:发起时刻 ≈ 工具结束 + 排队延迟 − 读取耗时 − 安全余量,且**只做 L3→L2,绝不预取进 L1**(这是和 TokenCake 的关键分歧:预取进 GPU 会和推理抢显存),块集合用 vLLM 自己的 token-hash 前缀标识,读请求走 miss / prefetch-refill / store 三条 FIFO 队列。**Protect**:L2 的驱逐优先级 CACHED > BACKUP > PREFETCHED,保护在被复用或 120s TTL 后解除,并留 256 块(约 1.5 GiB)余量;L2 对 L1 **不再保持包含关系**(DRAM 不存 GPU 已有块的副本),L3 仍包含且异步写入,再配一个 watch list 式 victim cache——盯住"在 L1 但不在 L2"的前缀块,L1 一驱逐就从 L3 回填到 L2。基于 **vLLM v0.24**,在 offloading connector 上加约 3,000 行,外加一个 `/kv_cache/prefetch` 端点。
  - 关键数据点:动机测量(Qwen3-30B-A3B、单卡 H100 NVL、vLLM 基线)——该模型 KV 约 **96 KiB/token**,50K 上下文就是 4.6 GiB,扣掉权重后约 32 GiB 可用 KV 只装得下约 6 个上下文;20 个并发 agent 时聚合 KV 工作集达 **127 GiB(≈ HBM 的 4x)**,GPU 上实际只有 4–9 个请求在跑,**最多 14 个 agent 在等、其中 54–74% 是在等 KV 加载**,token 来源最多 78% 落到 SSD,**最多 76% 的请求在首 token 前卡在 SSD 读上**;工具调用中位延迟可达 10s,而 LRU 下空闲块在 L1/L2 活不过一次工具调用。效果:工具延迟预测 18.5K 次调用上 **MAE 1.1s vs TokenCake 7.6s、MAPE 21% vs 117%**(预测器不到 300 行 Python);P95 TTFT 相比"vLLM + SSD 层"在四个 agent benchmark(DeepResearch Bench / GAIA / Terminal-Bench 4.0 / BrowseComp-Plus)上降 **35% / 49% / 23% / 33%**,相比 TokenCake 与 Continuum+LMCache 的尾部降 **77% / 86%**;吞吐相比 vLLM+L3 升 18%/40%/31%(TB4 持平),相比 TokenCake 2.9x、Continuum 3.5x;**KV 在 DRAM 命中率 96–100%**(GAIA-20 为 87%、BC+-20 为 60%),而 vLLM+L3 只有 5–39%,精确率 97–100%;整体落在"知道真实工具延迟的 Oracle"的 5% 以内。
  - 对我们的启示:这是本周对我们推理平台**最可落地**的一篇——它不要求新硬件、不改模型、不改 attention kernel,改的是 KV 分层的**准入与预取时机**,而且是在 vLLM 的 offloading connector 这个我们本来就要接的位置上。产品决策级动作:(1) **把"工具调用延迟"变成调度器的一等输入信号**。这需要产品侧做一件我们一直没做的事:**在网关/agent runtime 与推理引擎之间开一条通路**,把"这个会话正在等哪个工具、预计多久返回"透传给 KV 管理器(论文的 `/kv_cache/prefetch` 端点就是这条通路的最小形态)。谁先把这条链路打通,谁的 agent 场景 TTFT 尾部就比对手低一半。(2) **预取的目标层必须是 DRAM 而不是 GPU**——这条结论可以直接写进我们 KV 分层的设计约束,省掉一轮"预取进显存反而更慢"的弯路。(3) **L2 对 L1 放弃包含关系 + victim cache 回填**,是我们现有 KV 分层实现里值得立刻改的一处:DRAM 不该浪费在 GPU 已有的块上。(4) 注意局限:全部实验是**单卡**,多卡/多实例下"预取窗口 vs 请求被路由到别的 replica"会和 router 的 KV 亲和策略打架——这正好和本期 llm-d 那篇的 router 问题接上,我们做方案时要把两者放在一张图上设计。
  - 代码:论文未给仓库地址。

- **[Towards Fair Resource Sharing in Agentic LLM Serving](https://arxiv.org/abs/2611.23558)**(11-17,系统名 Duru)— 公平性该按 agent 算还是按 request 算?作者证明按 request 公平不等于按任务公平,基线直接打的是 **NVIDIA Dynamo 和 llm-d**。
  - 核心思路:agent 会话是一串前后依赖的 LLM 调用,**每次调用上的小延迟会累积成任务级的大延迟**,所以 token 级/请求级公平(如 VTC)看起来均匀,端到端任务完成时间却可以严重不均。作者把公平定义为**相对单独执行的 slowdown**(因为 agent 会话不适合用绝对延迟 deadline),在线用"等待时间 + 已完成工作量"算一个归一化 slowdown(standalone 时间查离线延迟表,**不需要预测未来请求或剩余时间**)。Duru 把这个信号同时喂给 **router 的准入**和**runtime 的调度**:候选按 slowdown 降序排、router 在工作集预算内准入,并加"饥饿例外"——等待中 slowdown ≥ α(建议 α = 1)就强行准入、临时放宽预算(以保住 KV 复用为前提),再叠一层 **slowdown 驱动的扩缩**(p99 信号达到目标值 5 就加一个 GPU worker,扩容 30s 冷却、空闲 300s 且无排队才缩)。
  - 关键数据点:硬件实测先给出一条产品侧很有用的结论——**不同模型的"受害模式"完全不同**:8×MI300X / 8×H200、TP=8,固定聚合上下文 983,040 token 把 batch 从 8 拉到 384,DeepSeek 的 decode 延迟涨 **3.3x**,而 Qwen 只涨 1.5x、Llama 1.7–2.3x;反过来固定 batch=32、把单请求上下文从 3,840 拉到 122,880,Qwen/Llama 涨 **2.7–3.8x** 而 DeepSeek 只涨 1.1x。即**DeepSeek 怕批量、Qwen/Llama 怕长上下文**。效果:跨 15 个"模型×负载×硬件"组合(MI300X / H100,模型 Qwen3-Coder-30B-A3B / Llama-3.3-70B / DeepSeek-V4-Flash,负载 Azure GitHub Copilot trace / TraceLab / AgentX),p99 归一化 slowdown 几何平均降 **44.4%**、最高 **79.5%**(15 个里 14 个降 13.8–79.5%,唯一例外是 Qwen+H100+Azure 反而变差),同时吞吐维持在基线的 **91.8–127.4%**;48 小时生产 trace 重放上 **agent 级 SLO 达标 97.4% 且用的 GPU 比 Dynamo 少**。实现跑在 vLLM 0.28.0 + LMCache 0.5.4,基线含 Dynamo KV-aware routing、llm-d::VTC、Dynamo::ThunderAgent、FCFS、Continuum 等。
  - 对我们的启示:(1) **我们的多租户配额/公平性语义要升一级**:现在业界(含我们)普遍做到"按 token 或按请求的加权公平",这篇说明在 agent 场景下这个口径会系统性地偏袒调用次数少的任务,正确的计费/公平单位是**会话(任务)级 slowdown**。这是一个可以写进产品需求的定义变更,而且它只需要"等待时间 + 已完成工作量 + 离线 standalone 延迟表",**不需要预测剩余长度**,实现代价远低于预测式方案。(2) **扩缩容的触发指标应该是 agent 级 slowdown 的 p99,而不是 GPU 利用率或 QPS**——这和 11-02 那期 InferScale 的"SLO 感知扩缩"是同一条线,但 Duru 给了多租户公平这一维。(3) 那组**模型敏感度实证最该马上用起来**:同一个集群上混跑 DeepSeek 与 Qwen/Llama 时,限流维度要分开——对 DeepSeek 卡 batch、对 Qwen/Llama 卡单请求上下文长度。这可以直接做成我们调度器里的 per-model 准入策略模板。(4) 基线选了 Dynamo 与 llm-d,说明**这两家已经是 agent 服务公平性的学术参照系**,我们对标时的对象也应该是它们而不是裸 vLLM。

## 值得泛读(10 篇)

- [Making Preemption Productive in Long-Output LLM Serving](https://arxiv.org/abs/2611.20106)(11-15,系统名 Stint)— 推理模型输出极长(IMO 题中位 17,089 token),KV 在显存里待几分钟,显存一满就被抢占、反复丢失再恢复("KV thrashing")。实测 vLLM 重算 / LMCache / SGLang HiCache **都有 21–23% 的请求卡住超过 1 分钟**、约六分之一超过 5 分钟,重算路径下一次暂停能占请求生命周期的 72%。Stint 在 vLLM 0.9.2 上加 CPU KV 快照池(按当前块数精确预留的连续 pinned extent、best-fit)+ 按年龄(5s)readmission 并保护到吐出 64 个新 token + 用 hidden states 估剩余长度来选 victim(SRJF)。8×H200(DP4/TP2)、Qwen3-32B:**p99 TPOT 降 50.7%**、吞吐 +12.0%(对比同引擎重算基线),最长暂停从重算的 808s 压到 **不超过 49.3s**;代价是 mean TTFT 高 14.8%、pinned host memory 从 328 GiB 涨到 1,357 GiB,且 arXiv 摘要类高速率负载反而低 19–21%。我们做推理平台的抢占策略时,这是"抢占不可避免、但要让它有产出"的参考实现。
- [Harvesting Expert-Parallel Bubbles for Fine-Tuning](https://arxiv.org/abs/2611.24496)(11-18,系统名 BubbleTea)— MoE 专家并行做完 SOTA 负载均衡后,层内气泡仍占 prefill 时间 **8–13%**(8k prefill 约 0.29ms/层,decode 的 5–25µs/层太小没法用)。每张卡都看得到完整 top-k 路由结果,于是用 ⌈n_e/M⌉ 个 tile 预测本层气泡(中位误差 8.9µs ≈ 气泡的 7%,服务路径开销 ≤0.5%),再用编译期 pass(把推理 kernel 换成可微等价物 + AOTAutograd 导反向 + 按 roofline 切 ≤50µs 的 chunk + CUDA graph 捕获)把 LoRA 微调切成能塞进气泡的碎片,**复用已加载的服务权重**(否则 Qwen3-30B-A3B 要多约 15 GB/卡)。4×A100-80G + vLLM:微调吞吐 **1.9–6.2x LLMStation**,p90 推理延迟在 63 个负载中 50 个保持在单独服务的 10% 以内(LLMStation 44 个);生产突发 trace 上 3.3x LLMStation、14x MPS 下的裸 trainer。
- [TideCache: Efficient Hybrid LLM Serving with Transparent Cache Management and Layer-Wise Streaming](https://arxiv.org/abs/2611.26619)(11-19)— 面向 CPU-GPU 超级芯片上的混合注意力模型(全局注意力层 + 有界状态层):透明缓存池在不同缓存组件间重分配 GPU 页,Cache Streamer 利用有界状态层的计算窗口预取下一个全局注意力层的前缀,调度器在"常驻执行 / 流式执行"间选。**GB300 与 GH200 上 7 种模型/平台组合,agent 轮次完成量最多 2.04x,整体 P50 per-token 延迟降 20–59%,agent P50 TTFT 改善 1.40–3.05x**,基线是 SGLang + HiCache。Grace/GB 这类超级芯片要进我们硬件矩阵时的直接参考。
- [Held While Waiting: What LLM Agent Sessions Reserve on Serverless and Agent Runtimes](https://arxiv.org/abs/2611.26480)(11-19)— 在 Amazon Bedrock AgentCore 上实测:agent 每次等模型回复**中位 2.7 秒,自身只算 5–40ms**,而 AgentCore 为每个会话独占一个 VM 级环境直到会话关闭——1,000 个会话占 1,000 个环境,干的活只需 2–15 核;客服场景会话平均 33 秒,环境却被额外攥住 **15 分钟**。仿真显示 64 个会话共享一个环境可少用 **59x** 环境,99% 的回复只多等 ≤40ms。作者还点出三种天真测法(打桩模型、围模型调用计时、背靠背步进)都会把计算时间测低。对我们要做 agent runtime 的密度与计费模型是硬数据:**按会话独占沙箱 = 卖给客户 59 倍的空气**;但共享需要平台侧支持,被调研的 agent runtime 里只有一家部分支持。
- [Benchmarking LLM Inference on Desktop-Scale NVIDIA Grace Blackwell Clusters](https://arxiv.org/abs/2611.20289)(11-15)— 两台 DGX Spark GB10 + 200GbE,17 个开源权重 checkpoint(8B–235B,dense 与 MoE,4 种权重精度)在 vLLM 上做 TP=2 / PP=2 / 双副本对照,并发 1–64、每配置独立启动三次。**TP=2 对单机峰值吞吐的中位增益 1.59x,PP=2 只有 1.39x**,96 组匹配对照里 TP=2 赢 93 组;空载 inter-token 延迟为单机的 0.52–0.73x(PP=2 几乎无改善);**同并发下单机的每输出 token GPU 能耗更低**,而且**单机上开 NVFP4 比"加第二台机器跑 BF16"更能降空载延迟**。代码与数据开源(github.com/kevinhbhimani/dgx-spark-llm-serving-benchmark)。给私有化/边缘小集群做选型与"该加机器还是该量化"这类客户问题的现成答案。
- [A Runtime System for Mitigating Crossbar Port Contention on SM-Partitioned GPUs](https://arxiv.org/abs/2611.24458)(11-18,系统名 GPCPlace)— CUDA Green Contexts 做 SM 划分时,把负载"摊开"还是"打包"到 GPC 上没有普适最优解;GPCPlace 在目标 GPU 上 profile 出两种放置各自的 slowdown,运行时选一种并通过 hook CUDA driver 的 kernel launch 设置 SM mask,**不改应用**。**14 张 GPU、112 个负载组合上,延迟敏感负载相对 Green Contexts 平均最多 1.15x、最高 2.38x,且不掉吞吐**。我们 HAMi 侧做 SM 级切分时,"放哪些 SM"和"分多少 SM"是两个独立旋钮,这篇量化了前者。
- [eFAIR: Fair LLM Serving under Hourly Electricity Commitments](https://arxiv.org/abs/2611.24119)(11-18)— 在"日前小时级电力承诺"约束下做在线调度:定义每请求的归一化吞吐,把公平建成 leximin 优化,协同请求分派、电力预算分配与 GPU 频率选择。**H20 与 H200 各 32 副本:归一化吞吐的第 10 百分位相对最优的预算可行基线提升 28.0–31.0%,对小时级电力承诺的绝对偏差 <0.26%**。国内客户越来越多遇到园区/机房的用电配额与分时电价,这给"把电力预算当一等调度资源"提供了可照抄的目标函数。
- [ScaleBench: An Extensible and Reproducible Experimental Platform for Kubernetes Autoscaling Research](https://arxiv.org/abs/2611.24398)(11-18)— 把 autoscaler 当原生 K8s 资源(manifest 模板 + 注册表 + 环境变量传参,Operator 列为 future work)来可复现地评测,这样**集成成本也能一起被量化**。两节点 K3S + Online Boutique + Locust/Wiki trace 的案例研究给出一个让人清醒的结果:**默认 HPA(CPU 目标 50%)的 500ms SLO 违约率 1.00% 最低,研究型 PBScaler 高达 29.50%**(DAS 4.50%、HPA-80 4.71%),PBScaler 还多花约 3x CPU。注意它只测通用微服务、未涉及 LLM/推理扩缩(开源在 github.com/ZeWang42/Swarmchestrate-Decentralised-Auto-Scaling)。对我们的用处是方法论上的:**我们自研的推理 autoscaler 必须和"调好参的默认 HPA"同台比,否则很容易输给默认值还不自知**。
- [How well does graph superoptimization transfer? Adapting tensor-graph superoptimizer to a Triton-based NPU](https://arxiv.org/abs/2611.22844)(11-17)— 把 Mirage(图级超优化器,原为 CUDA 设计)经 Triton 编译栈移植到**华为昇腾 910B3**,在 MatMul / softmax / RMSNorm+MatMul / gated MLP / FNN / attention 上实测:图级优化**能迁移**,融合类负载相对可得参考实现最多好 **87.0%**,但强依赖张量形状与负载结构,其他配置下有大幅回退。作者结论是"可移植的图表示 ≠ 可移植的优化空间",瓶颈在目标专属的张量切分、执行资源建模、后端下降与融合、以及搜索/验证成本(MICRO 2026 FlagOS Forum)。我们昇腾线做编译优化时的现实预期管理。同周还有 [AscendGYM](https://arxiv.org/abs/2611.17621)(11-13)——48 个真实训练/推理 shape 的昇腾 kernel **优化**(非生成)benchmark,带 Speedup-Token Score 指标与搜索编排 harness,开源在 github.com/SLAI-AITP/AscendGYM。
- [Measuring and Charging for Retained Context in Long-Context LLM Services](https://arxiv.org/abs/2611.24071)(11-18)— 长上下文服务按"重复上下文"计费,但计费权重未必对应该上下文对答案质量的真实贡献。作者提出内容相关性 / 可观测代理 / 可审计位置权重三层框架,消融实验显示**相关性比位置更重要,各种"距离衰减"权重族都打不过纯相关性基线**;实测栈上 65,536 token 时缓存命中把重复前缀的计算量压掉 **两个数量级以上**,而冷重传限制了折扣上限;标定仿真下 **P99 会话费用可降 31–42%**。我们要做"按 token 计量 + 配额"的网关时,这是少见的把"缓存命中该不该给客户折扣"量化出来的工作(作者自述是有界的 per-token 记账规则,不是已验证的效用估计器)。

## 趋势观察

- **本周最强信号:agentic 负载正式成为 serving 系统论文的主战场,而且议题从"治理"下沉到"运行时"**。本窗口 cs.DC 里的 LLM 服务论文过半以 **agent 会话**而非单请求为对象:TripleKV(工具空窗期的 KV 该放哪)、[Aggron](https://arxiv.org/abs/2611.26435)(11-19,利用队头阻塞的空窗做 agent 上下文摘要压缩,高负载下 P99 程序延迟降 27–31%、吞吐 1.34–1.40x)、[Callo](https://arxiv.org/abs/2611.18459)(11-13,agent 改上下文导致 KV 失效后,把**失效的 KV 当 speculative draft** 用,相对 vLLM 全请求加速 1.05–1.19x)、Duru(公平性按 agent 算)、Held While Waiting(会话独占沙箱的浪费)、TideCache(以 agent 轮次为指标)、Validation-driven(以 agent trace 为定容输入)。共同点是:**"会话级状态 + 工具调用空窗"成了新的一等调度对象**。对照 11-02 那期——企业治理层(网关/OPA/配额/多厂商适配)在上期确立,本期这些议题整体下沉一层,变成"谁的 KV 该留、谁该被抢占、公平和计费按什么单位算"。我们的推理平台路线图应当据此调整优先级:**agent 会话的生命周期管理(KV 留存、沙箱复用、会话级配额)比再榨 10% 的引擎吞吐更值得投人**。
- **多租户 KV 共享的安全面被集中捅破,这是本期最该进产品风险清单的变化**。BlockJack(改一个 block table 表项即跨租户重定向,vLLM 2026-09-22 确认、与 Sonar 各自出补丁,Rowhammer 实测 49% 窗口成功)、When Shuffling Fails(KV 混淆方案被 100% 还原 token 多重集)、From Token Changes to Task Failures(共享前缀那一份物理 KV 块上单比特翻转的错误率量化)三篇同周出现。**prefix cache / KV 复用是过去两年推理性能收益的总来源,现在它第一次被系统性地证明是一条跨租户的数据与故障通路,而且元数据(一个表项)比数据本身更脆弱**。直接动作:prefix cache 跨租户复用改为显式可关、多租共享实例上默认关;block table 完整性校验与 vLLM 补丁版本写进受支持矩阵;高敏感租户不共享 serving 实例与块池。
- **"回收闲置算力"的粒度从卡/时间片下探到亚毫秒,且路线明确绕开"改内核/改驱动"**。Berth 在用户态靠喂给式节流 + 把时间片从 2,048µs 改写成 500µs,就让 15ms SLO 的推理与训练混跑达标率从 64.9%(裸时间片)/0.0%(MPS)提到 95.8%,同时 best-effort 吞吐是最近基线的 2.7–3.5x;BubbleTea 更进一步,在 MoE 专家并行的**层内** 0.29ms 气泡里塞 LoRA 微调 chunk。两篇都明确以"不改应用/框架/内核/驱动"或"编译期自动派生"为设计前提,因为作者都认定**闭源 GPU 栈的运营方没有改栈的权力**——这正是我们在客户现场的处境,所以这条路线对我们的可移植性远高于学术界过去那些改驱动的方案。
- **"平台怎么验证、怎么定容"第一次成为独立的论文议题,而且结论都是在打"默认做法"的脸**。Validation-driven(公开 trace 只够初始调参,用它定容会把并发高估约 2x、吞吐高估约 40%;且常规压测永远走不到 KV offload 的恢复路径)、ScaleBench(调好参的默认 HPA 把研究型 autoscaler 打得很惨:1.00% vs 29.50% SLO 违约)、Grace Blackwell 桌面集群实证(TP=2 中位 1.59x > PP=2 的 1.39x;单机开 NVFP4 比加第二台机器更能降延迟)、以及 [LEDGE](https://arxiv.org/abs/2611.24085)(11-18,异构边缘分布式服务的模拟器,请求级 MAPE <3.6%、比真机快 135.3x,开源)和 AscendGYM。这一波对我们的意义很直接:**售前容量模型、自研 autoscaler、硬件选型建议这三件事,现在都有了公开的、更严格的对照方法,我们应当主动用它们自测,而不是等客户拿这些论文来问**。
- **能效与计量继续加厚,并开始和"电力合约""计费公平"这种商务条款挂钩**。eFAIR(日前小时级电力承诺下的 leximin 公平,偏差 <0.26%)、[A Matter of Stages](https://arxiv.org/abs/2611.21165)(11-16,多模态服务里 EPD 三段分离在同样三卡预算下每成功请求 GPU 能耗降 13.3–37.0% 但平均 TTFT 升,统一降频到 80% 降能耗 11.7–18.6%)、Measuring and Charging for Retained Context(缓存命中该折扣多少、P99 会话费用可降 31–42%)。延续 11-02 的 Token-Energy 线,但重心从"每 token 多少焦耳"转向"这些焦耳和这些 token 怎么变成合约和账单"——这正是我们网关层计量/配额模块该吸收的部分。
- **一条顺带观察:大量工作已经默认"在 vLLM / SGLang 上改"而不是自造引擎**。本期 TripleKV(vLLM v0.24 的 offloading connector,约 3,000 行)、Stint(vLLM 0.9.2)、Duru(vLLM 0.28.0 + LMCache 0.5.4)、BubbleTea(vLLM)、TideCache(SGLang + HiCache)、XM-Sparse([2611.22280](https://arxiv.org/abs/2611.22280),SGLang)、[Gemma 4 K=V 单份存储](https://arxiv.org/abs/2611.23035)(11-17,vLLM 原型,32K–64K 下稳态 KV 内存降至 1/1.34–1/1.40 且 attention kernel 不改)全是在上游引擎上做增量。这对我们的工程策略是正反馈:**把能力做成 vLLM/SGLang 的 connector / plugin 层,既是学术界的默认接口,也是我们把差异化能力跟上上游节奏的唯一可持续方式**。
